## 1. Overview

The repository holds no Unity project yet, so `v0.1.0` first bootstraps one (Unity 6.3 LTS, URP with the 2D Renderer,
Input System, uGUI/TextMesh Pro) with the standalone .NET Core test project and `tools/verify-all.sh`. On top of that:

- **`Murim.Core`** generates the valley from a 32-bit seed using integer-only arithmetic. The valley stays a genuine
  multi-level world: a 512 m × 512 m heightfield at 1 m resolution with three tiers, water features, surface weights,
  and prop instances that each carry a ground position and a height. Core also owns the fixed oblique projection that
  maps that world onto the 2D screen plane (§2.1), the back-to-front prop order (§3.2.5), and the camera motion model
  (pan, drag, zoom, reset, bounds) as a pure, frame-stepped state machine working in screen-plane coordinates.
- **`Murim.View`** draws that world **strictly in 2D** (§3.3.1): one orthographic camera that never rotates, a flat
  painted terrain layer, flat water shapes, one painted sprite per prop with a soft ground-shadow sprite, and a
  painted sky and horizon backdrop. There are no 3D models, no lights, and no depth buffer; draw order is fixed at
  launch. View also resolves the seed, loads tunables, feeds input into the Core camera rig, and shows the `Esc`
  overlay.

**Compatibility.** First version: there are no earlier saves, configs, or dev commands to preserve. Seeds are only
guaranteed to reproduce a valley within the same build and the same `world.json`.

**External surfaces (untrusted input).** Two JSON files under `Assets/StreamingAssets/Data/` and the `-seed`
command-line argument (§2.5, §3.1.1). No networking, saves, telemetry, crash upload, or mod surface.

**Logs and privacy.** Game log lines carry seeds, hashes, counts, timings, config file names, and field names only;
never local paths, user names, or machine names (§2.6).

**Developer controls.** None. `v0.1.0` ships no dev console, debug command, cheat, or debug overlay, so nothing needs
gating; release builds are additionally built without `Development`, `AllowDebugging`, or Profiler options (§3.6.4).
The seed override is a product feature (F-01) and stays available in release builds.

## 2. Conventions and shared contracts

### 2.1 Units and coordinates

**Logical world** (rules, generation, future building and flight):

- **+X = east, +Z = north, +Y = up.** 1 unit = 1 metre.
- The generated terrain rectangle `T` spans `x, z ∈ [0, 512]` m. Core stores positions and heights as **integer
  centimetres** (`…Cm`) and grid data per vertex on a 513 × 513 grid indexed `z * 513 + x` (x, z in metres).
- Fixed point "Q10" means an integer where `1024` = 1.0.

**Screen plane** (everything that is drawn or pointed at). The view is a fixed oblique projection looking north from
36.87° above the horizon (a 3-4-5 triangle, so every factor is an exact fraction):

```text
u = x                                   // east stays horizontal, 100 %
v = 0.6 * z + 0.8 * y                   // ground depth at 60 %, height at 80 %, both pointing up the screen
```

- `Murim.Core.World.Projection.PlaneVCm(int zCm, int yCm) = (3 * zCm + 4 * yCm) / 5` (floor division) is the only
  implementation of this mapping; `u` in centimetres is `xCm`. View converts with `/ 100f`.
- Unity world space **is** the screen plane: Unity `X = u`, `Y = v` in metres, `Z = 0` for every world renderer. North
  and up both point up the screen, so higher tiers and more distant ground sit higher on screen.
- World art is authored at `Projection.PixelsPerMetre = 128` pixels per plane metre (§4).

### 2.2 Determinism rules

- `ValleyGenerator.Generate(seed, config)` uses **only** 32/64-bit integer arithmetic (`unchecked`), `Isqrt`, and the
  primitives in §3.1.2. No `float`/`double`, no `System.Random`, no clocks, no threads, no `GetHashCode()`, no
  dictionary/hash-set iteration order.
- In §3.1–§3.2 every `/` is **floor division** (`FloorDiv`, rounding toward −∞) and every `>>` is an arithmetic shift.
  Loops over the grid run `z` outer, `x` inner, ascending.
- The Core camera model (§3.4) is not part of seeded generation and uses `float`. It calls no `Math`/`MathF`
  transcendental functions (project invariant for all of `Murim.Core`); the 2D model needs none.
- The same seed and `world.json` produce the same `ValleyWorld.Hash` in the standalone .NET test host, the Unity
  Editor, and the built player (T-CORE-05, T-ENG-03, T-BLD-02).

### 2.4 Layers, scene and draw order

No custom layers, tags, or sorting layers. World renderers use layer index `0`; the overlay canvas uses layer index
`5`. No code looks layers up by name. The single scene is `Assets/Scenes/Valley.unity`.

Nothing in the world uses a depth buffer. What is drawn in front is decided only by `Renderer.sortingOrder` on the
default sorting layer, set once at launch from the constants in `Murim.View.DrawOrder` (lower draws first):

| Band | Content | `sortingOrder` |
|---|---|---|
| `Backdrop` | horizon backdrop quad (§3.3.5) | `-32000` |
| `Terrain` | 64 terrain chunks (§3.3.2) | `-31000 + (7 - chunkRow)`; `chunkRow` 0 = southernmost, so north rows draw first |
| `Water` | stream, brook, and pools `-30000`; waterfall `-29999`; foam collar `-29998` (§3.3.3) | as listed |
| `Lips` | `bank_lip` sprites | `-29000 + lipRank` |
| `Shadows` | every ground-shadow sprite | `-28000` |
| `Props` | every other prop sprite | `-16000 + propRank` |

`lipRank` and `propRank` come from `PropOrder.BackToFront` (§3.2.5): `0` is the northernmost. Family caps (§3.2.3)
keep `lipRank ≤ 499` and `propRank ≤ 13,599`, so every value fits the signed 16-bit range of `sortingOrder`. The
`Esc` overlay is a Screen Space Overlay canvas and draws above the world.

### 2.5 Configuration loading

Two files, both optional at runtime, both shipped with their defaults:

| File | Owner section | Consumed by |
|---|---|---|
| `Assets/StreamingAssets/Data/world.json` | §3.1.9 | `ValleyGenerator` |
| `Assets/StreamingAssets/Data/camera.json` | §3.4.8 | `CameraRig` |

`Murim.View.JsonConfigLoader.TryLoad<TDto>(string fileName, out TDto dto)` applies these rules in order; any failure
logs **one** warning naming the file name and the reason code, and the caller uses the built-in defaults for the
**whole file** (no partial application):

1. `fileName` must be one of the two literal names above. The path is always
   `Application.streamingAssetsPath + "/Data/" + fileName`; no caller-supplied directories, no `..`.
2. Missing file → reason `missing`.
3. File length above `65536` bytes (64 KiB) → reason `oversized`; the file is not read.
4. Bytes decode as UTF-8 (a leading BOM is skipped). `JsonGuard.MaxDepth(text)` (counts `{`/`[` nesting outside
   string literals) above `4`, or unbalanced nesting → reason `malformed`.
5. `JsonUtility.FromJson<TDto>` throws → reason `malformed`. DTOs are flat `[Serializable]` classes of `int`/`float`
   fields; unknown JSON fields are ignored.
6. `schemaVersion != 1` → reason `schema`.
7. Core validation (`WorldConfig.TryCreate` / `CameraConfig.TryCreate`) rejects any field outside its range (§3.1.9,
   §3.4.8), any non-finite float, or any violated cross-field rule → reason `range:<fieldName>`. Because every valid
   range excludes `0`, a missing field (deserialised as `0`) is rejected by this step.

`float` fields are parsed by `JsonUtility` (culture-independent). Any other numeric parsing in the project uses
`CultureInfo.InvariantCulture`. The loader reads through one internal file-access delegate (file name → length and
bytes) so engine tests can supply file contents without touching the shipped files.

### 2.6 Logging

All game logging goes through `Murim.View.GameLog.Info/Warn(string)`, which prefixes `[Murim] `. Messages are built
only from: literal text, seeds, hashes, counts, millisecond timings, the two config file names, field names, and
exception **type names** (never `Exception.Message` or stack traces, which can contain absolute paths). Required lines:

| When | Line |
|---|---|
| World built | `[Murim] World ready seed=<uint> source=<cli or random> hash=<16 hex digits> props=<int> ms=<int>` |
| Config fallback | `[Murim] Config <fileName> ignored (<reason>); using defaults.` |
| Bad seed argument | `[Murim] Ignoring invalid -seed value; using a random seed.` (the raw value is not echoed) |

### 2.7 Developer controls

None exist in `v0.1.0`. If a later version adds any, they must be compiled out of release builds with
`#if UNITY_EDITOR || DEVELOPMENT_BUILD`.

## 3. Feature design

### 3.1 Valley generation (F-01)

`Murim.Core.World.ValleyGenerator.Generate(uint seed, WorldConfig config)` returns an immutable `ValleyWorld`. It is a
constructive pipeline (no rejection sampling): every seed yields a valid valley. Stages run in the order below. The
valley is generated as real multi-level space (positions and heights); the 2D presentation in §3.3 only projects it.

**Shape in one paragraph.** The valley is an amphitheatre opening south toward the viewer. A parabolic basin tongue
runs north from the south edge to its head near the centre; the mid tier wraps around it; the upper tier wraps around
that; ridges rise along the west, east, and north edges. Because tier level never decreases northward (§3.1.3), every
embankment faces south, so it is seen front-on and higher tiers always step up the screen (F-03, ART-002). A
spring-fed brook crosses the mid tier and drops as the single waterfall into a plunge pool at the basin head; the main
stream meanders south and leaves at the south edge. One gentle ramp connects basin to mid tier and one connects mid to
upper tier, on opposite sides of the valley axis.

#### 3.1.1 Seed (EC-10)

- `Murim.Core.Common.SeedArgument.TryParse(IReadOnlyList<string> args, out uint seed)` returns `Absent`, `Valid`, or
  `Invalid`. It uses the first argument equal to `-seed` (ordinal, case-sensitive) and the argument after it. Valid
  values are 1–10 ASCII digits parsing (`NumberStyles.None`, invariant culture) to `0 … 4294967295`. A missing value,
  any other character, more than 10 characters, or overflow is `Invalid`.
- `Murim.View.SeedSource.Resolve()` passes `Environment.GetCommandLineArgs()` (through an internal delegate that
  engine tests replace): `Valid` → that seed (`source=cli`); `Absent` → 4 bytes from
  `System.Security.Cryptography.RandomNumberGenerator` as a little-endian `uint` (`source=random`); `Invalid` → the
  warning in §2.6, then a random seed.
- Example: `MurimLifeGame.exe -seed 20261127`. The seed and world hash of every launch appear in the log (§2.6), so a
  normal launch can be reproduced later.

#### 3.1.2 Primitives

```text
Pcg32(seed, stream)        PCG-XSH-RR 64/32. inc = (stream << 1) | 1; state = 0; Next(); state += seed; Next().
  Next():                  old = state; state = old * 6364136223846793005 + inc;
                           xs = (uint)(((old >> 18) ^ old) >> 27); rot = (int)(old >> 59);
                           return (xs >> rot) | (xs << ((-rot) & 31));
  Bounded(n):              thr = (uint)(-n) % n; loop { r = Next(); if (r >= thr) return r % n; }
  R(lo, hi):               lo + Bounded(hi - lo + 1)                      // inclusive

Hash32(int x, int z, uint salt):
  h = (uint)x * 0x9E3779B1 ^ (uint)z * 0x85EBCA77 ^ salt * 0xC2B2AE3D;
  h ^= h >> 16; h *= 0x7FEB352D; h ^= h >> 15; h *= 0x846CA68B; h ^= h >> 16; return h;

Salt(k)   = Hash32(k, 0x51ED, seed)
S(t)      = (t * t * (3072 - 2 * t)) >> 20            // Q10 smoothstep, t in [0, 1024], 64-bit intermediate
Clamp01(t)= clamp(t, 0, 1024)
Isqrt(a)  = floor(sqrt(a)) for 64-bit a >= 0, computed with integers only

Noise(x, z, cell, salt):                               // x, z >= 0 in metres; result in [-1024, 1023]
  ix = x / cell; iz = z / cell; fx = (x % cell) * 1024 / cell; fz = (z % cell) * 1024 / cell;
  c(i, j) = (int)(Hash32(i, j, salt) & 2047) - 1024;
  n0 = c(ix, iz)     + (((c(ix + 1, iz)     - c(ix, iz))     * S(fx)) >> 10);
  n1 = c(ix, iz + 1) + (((c(ix + 1, iz + 1) - c(ix, iz + 1)) * S(fx)) >> 10);
  return n0 + (((n1 - n0) * S(fz)) >> 10);

Bump(d, inner, outer):                                 // Q10; d = |distance| in metres
  d <= inner ? 1024 : d >= outer ? 0 : S((outer - d) * 1024 / (outer - inner))
```

Noise salts: `Salt(1)` contour wobble 64 m, `Salt(2)` wobble 24 m, `Salt(3)` basin 48 m, `Salt(4)` basin 16 m,
`Salt(5)` plateau 40 m, `Salt(6)` detail 8 m, `Salt(7)` ridge 32 m, `Salt(8)` ridge 12 m, `Salt(9)` bank type 56 m,
`Salt(10)` stone 36 m, `Salt(11)` soil 44 m, `Salt(12)` grove 56 m, `Salt(13)` flower 28 m. Prop rule `r` (§3.2.3)
uses `Salt(100 + r)` and `Salt(200 + r)`.

#### 3.1.3 Layout and tier field

Layout values are drawn from `Pcg32(seed, 1)` **in exactly this order** (metres):

| # | Draw | Result |
|---|---|---|
| 1 | `R(-40, 40)` | `axisX = 256 + draw` (valley axis) |
| 2 | `R(196, 228)` | `headZ` (basin head on the axis) |
| 3 | `R(96, 116)` | `midDepth` (mid tier depth on the axis) |
| 4 | `R(150, 190)` | `bowK` (contour bow at 176 m from the axis) |
| 5 | `R(-12, 12)` | `wfX = axisX + draw` (waterfall column) |
| 6 | `R(0, 1)` | `side = draw * 2 - 1` |
| 7 | `R(72, 124)` | `slope1X = clamp(axisX + side * draw, 112, 400)` (basin→mid ramp) |
| 8 | `R(72, 132)` | `slope2X = clamp(axisX - side * draw, 112, 400)` (mid→upper ramp, opposite side) |
| 9 | `R(-60, 60)` | `exitX = axisX + draw` (stream exit at the south edge) |
| 10–14 | `R(-22, 22)` × 5 | `off[1..5]` (stream meander offsets) |
| 15 | `R(-8, 8)` | `springX = wfX + draw` |

With `mid = config.midTierHeightM * 100` and `upper = config.upperTierHeightM * 100` (cm), per vertex `(x, z)`:

```text
dx     = x - axisX
P      = bowK * 100 * dx * dx / 30976                          // contour bow, cm
slopeQ = 2 * bowK * |dx| * 1024 / 30976;  g = Isqrt(1048576 + slopeQ * slopeQ)   // Q10 gradient length of v
wob    = ((Noise(x, z, 64, Salt(1)) * 1200) >> 10) + ((Noise(x, z, 24, Salt(2)) * 250) >> 10)
v      = 100 * z + P + wob                                      // "northness" field, cm
V1 = headZ * 100;  V2 = (headZ + midDepth) * 100
B1 = Bump(|x - slope1X|, 22, 48);  B2 = Bump(|x - slope2X|, 22, 48);  Wf = Bump(|x - wfX|, 4, 12)
hw1 = 450 + (((mid * 5 / 2 - 450) * B1) >> 10);  hw1 = hw1 + (((250 - hw1) * Wf) >> 10)
hw2 = 500 + ((((upper - mid) * 5 / 2 - 500) * B2) >> 10)       // embankment half-widths, cm
hwv1 = (hw1 * g) >> 10;  hwv2 = (hw2 * g) >> 10
s1 = S(Clamp01((v - V1 + hwv1) * 1024 / (2 * hwv1)));  s2 = S(Clamp01((v - V2 + hwv2) * 1024 / (2 * hwv2)))
e1 = (v - V1) * 1024 / g;  e2 = (v - V2) * 1024 / g             // signed distance to each boundary, cm
L  = s1 + s2                                                    // tier level, Q10: 0 basin, 1024 mid, 2048 upper
Ht = ((s1 * mid) >> 10) + ((s2 * (upper - mid)) >> 10)
```

Consequences the tests rely on:

- **Embankments** are smoothstep (rounded) drops: 9 m wide for the basin→mid step and 10 m wide for the mid→upper step
  (5 m wide at the waterfall, forming a cliff).
- **Gentle ramps** widen the same profile to `5 × step height` (60 m and 70 m at defaults) within 22 m of
  `slope1X`/`slope2X`, feathering out by 48 m: average gradient 0.20, smoothstep peak 0.30 before terrain noise.
- The wobble's north-south gradient is below 1 (0.56 + 0.31), so `v`, and therefore `L`, never decreases northward.

`ValleyWorld.TierLevelPct[i] = L * 100 / 1024` (`0`–`200`). `ValleyWorld.Slopes[0]` is measured on column
`x = slope1X` with `s1`, and `Slopes[1]` on column `x = slope2X` with `s2`: `Bottom` = the smallest `z` with `s ≥ 16`,
`Top` = the smallest `z` with `s ≥ 1008`, both stored in centimetres with `X = slopeX * 100`.

#### 3.1.4 Height composition

```text
fS    = S(Clamp01((z - 8) * 1024 / 48))                         // south mouth fade: 0 at z <= 8, 1 at z >= 56
tilt  = 200 + 150 * min(z, headZ) / headZ                       // basin tilts 1.5 m down toward the south
basin = tilt + ((Noise(x, z, 48, Salt(3)) * 60) >> 10) + ((Noise(x, z, 16, Salt(4)) * 25) >> 10)
und   = ((Noise(x, z, 40, Salt(5)) * 70) >> 10) + ((Noise(x, z, 8, Salt(6)) * 15) >> 10)
tW = Clamp01((72 - x) * 1024 / 72);  tE = Clamp01((x - 440) * 1024 / 72);  tN = Clamp01((z - 432) * 1024 / 80)
p(t)  = t * (t + 1024) / 2048;  rt = max(tW, tE, tN)
rough = ((Noise(x, z, 32, Salt(7)) * 250) >> 10) + ((Noise(x, z, 12, Salt(8)) * 60) >> 10)
ridge = max(side * p(tW), side * p(tE), north * p(tN)) / 1024 + ((rough * p(rt)) >> 10)
        // side = config.sideRidgeHeightM * 100, north = config.northRidgeHeightM * 100
H     = basin + ((fS * (Ht + ridge + ((und * min(L, 1024)) >> 10))) >> 10)
```

`ValleyWorld.RidgePct[i] = rt * 100 / 1024`. The ridges rise to their maximum at the terrain edge (30 m above the
local tier on the west/east edges, 26 m on the north edge at defaults). The south fade brings every tier and ridge
down to basin level at the south edge, so the row `z = 0` never exceeds 4 m (measured ≤ 2.8 m; needed by §3.1.7 and
§3.4.5).

#### 3.1.5 Water

```text
fallZ       = smallest z with s1(wfX, z) >= 512                  // cliff line on the waterfall column
zPool       = fallZ - 11
tiltAt(zm)  = 200 + 150 * min(zm, headZ) / headZ
plungeLevel = tiltAt(zPool) - 100;  brookLevel = mid + 180       // cm; waterfall drop = brookLevel - plungeLevel
```

| Feature | Definition (cm unless noted) |
|---|---|
| `PlungePool` | centre `(wfX, zPool)` m, radius `800`, level `plungeLevel` |
| `SpringPool` | centre `(springX, fallZ + 36)` m, radius `450`, level `brookLevel` |
| `Brook` | 16 nodes `i = 0..15`: `x = springX*100 + (wfX - springX)*100*i/15`, `z = (fallZ + 32)*100 - 2900*i/15`, half-width `150`, level `brookLevel` |
| `Stream` | Control points `C0..C6`: `z_k = z0 + (-800 - z0) * k / 6` with `z0 = (zPool - 8) * 100`; `x_0 = wfX*100`, `x_6 = exitX*100`, and for `k = 1..5` `x_k = clamp(wfX*100 + (exitX - wfX)*100*k/6 + off[k]*100, (axisX - lim_k)*100, (axisX + lim_k)*100)` with `lim_k = max(0, Isqrt(max(0, headZ - z_k/100) * 30976 / bowK) - 30)`. Phantom end points `2*C0 - C1` and `2*C6 - C5`. Each of the 6 segments is sampled at `j = 0..15` with the uniform Catmull-Rom below, plus the final point `C6`; nodes with `z < -400` are dropped. Node `i` of `n`: half-width `250 + 150*i/(n - 1)`, level `tiltAt(max(0, z/100)) - 100` |
| `Waterfall` | Width `300`. Nodes on column `x = wfX` every 50 cm from `z = (fallZ + 3)*100` down to `z = (fallZ - 3)*100`: `y = max(height(wfX, z) + 20, plungeLevel)`, with the first node's `y = brookLevel`. `height` is the final carved height, linearly interpolated between the two neighbouring vertices in `z` |

```text
CatmullRom(P0, P1, P2, P3, j) per coordinate, j in 0..15:
  (8192 * P1 + (P2 - P0) * j * 256 + (2*P0 - 5*P1 + 4*P2 - P3) * j * j * 16 + (3*P1 - P0 - 3*P2 + P3) * j * j * j) / 8192
```

**Carving.** Two passes change `H`: first `Brook` + `SpringPool`, then `Stream` + `PlungePool`. For each vertex
(position in cm), over the pass's path segments in node order and then its pool:

```text
segment a→b:  den = (b - a)·(b - a);  t = Clamp01(((p - a)·(b - a)) * 1024 / den)          // Q10, skip if den == 0
              q = a + (((b - a) * t) >> 10);  delta = Isqrt(|p - q|^2)
              hw = a.hw + (((b.hw - a.hw) * t) >> 10);  level likewise;  e = delta - hw
pool:         e = Isqrt(|p - centre|^2) - radius;  level = pool level
keep the candidate with the smallest e (first wins ties)
a = S(Clamp01((600 - e) * 1024 / 400));  c = S(Clamp01((200 - e) * 1024 / 250))
H = H + (((level + 50 - H) * a) >> 10)          // shape banks to 0.5 m above water within 2–6 m of the edge
H = H + (((level - 70 - H) * c) >> 10)          // carve the bed to 0.7 m below water
```

After both passes `H = clamp(H, 0, 12000)` and `wd` (per vertex, cm) = the minimum over both passes of `max(e, 0)`.
Both water levels sit at or below the lowest undisturbed ground of their tier (basin floor nominal ± 0.85 m, mid
plateau nominal ± 1.7 m), so no dry ground lies below adjacent water.
The waterline falls about 0.9 m outside the nominal half-width, where the bank meets the water at roughly 36°. The
water shapes (§3.3.3) fade out across that line, so water meets land with a soft painted edge and no hard seam
(ART-003).

#### 3.1.6 Surface weights

Eight terrain layers per vertex, bytes summing to `255`, in `ValleyWorld.SurfaceWeights[i * 8 + layer]`:

| Layer | Surface | Art |
|---|---|---|
| 0 | moss meadow turf | ART-001 |
| 1 | damp dark-slate soil | ART-001 |
| 2 | mossy stone floor | ART-001 |
| 3 | streamside pebble bank | ART-001 |
| 4 | grassy embankment face | ART-002 |
| 5 | earth-and-boulder bank face | ART-002 |
| 6 | hillside slope | ART-002 |
| 7 | ridge forest floor | ART-008 |

```text
gx = H(x+1, z) - H(x-1, z);  gz = H(x, z+1) - H(x, z-1)   (indices clamped to the grid);  G = Isqrt(gx*gx + gz*gz) / 2   // grade, %
b   = S(Clamp01((G - 45) * 1024 / 45))                           // bank face
eb  = S(Clamp01((Noise(x, z, 56, Salt(9)) + 256) * 1024 / 512))  // 0 grassy bank, 1024 earth-and-boulder bank
so  = S(Clamp01((Noise(x, z, 44, Salt(11)) - 200) * 1024 / 360))
st  = S(Clamp01((Noise(x, z, 36, Salt(10)) - 380) * 1024 / 260))
m   = S(Clamp01((G - 15) * 1024 / 30))
site_k = (B_k * ((4 * s_k * (1024 - s_k)) >> 10)) >> 10          // k = 1, 2
hl  = max(site_1, site_2, (m * 614) >> 10)
r   = S(Clamp01((rt - 150) * 1024 / 350))
w   = S(Clamp01((350 - wd) * 1024 / 300))
```

Start with `weight[0] = 1024` and all others `0`. Apply these overlays in order — `(1, so)`, `(2, st)`, `(6, hl)`,
`(7, r)`, `(4, (b * (1024 - eb)) >> 10)`, `(5, (b * eb) >> 10)`, `(3, w)` — where applying `(layer, a)` means: every
weight becomes `(weight * (1024 - a)) >> 10`, then `weight[layer] += a`. Finally `byte_k = weight_k * 255 / sum`, and
the remainder `255 - Σ byte_k` is added to the layer with the largest `weight_k` (lowest index on ties). No layer
depicts a footpath, road, or paving, and nothing in the generator produces linear worn tracks.

#### 3.1.7 View frame and relief shade

These are the only generation outputs that exist for the 2D presentation. All use `Projection.PlaneVCm` (§2.1).

| Value | Definition (cm in the screen plane) | Used by |
|---|---|---|
| `PlaneBottomCm` | `max` over `x = 0..512` of `PlaneVCm(0, H(x, 0))`: the highest point of the terrain's south (bottom) edge | camera bounds (§3.4.5) |
| `PlaneCrestCm` | `min` over `x = 0..512` of `PlaneVCm(51200, H(x, 512))`: the lowest point of the north ridge crest | camera bounds, haze (§3.3.1) |
| `VistaUCm` | `wfX * 100` | default view (CE-4) |
| `VistaVCm` | `PlaneVCm((fallZ + 3) * 100, brookLevel) - 440` | default view (CE-4) |

In every column `x` the projected terrain covers the whole span from `PlaneVCm(0, H(x, 0))` to
`PlaneVCm(51200, H(x, 512))` without gaps (the heightfield is continuous), so the plane rectangle
`u ∈ [0, 512] m`, `v ∈ [PlaneBottomCm, PlaneCrestCm]` is always fully covered by terrain. `PlaneBottomCm ≤ 320`
because the row `z = 0` never exceeds 4 m (§3.1.4). At defaults `PlaneCrestCm / 100` is about 348–352 m.

The vista centres the default view on the waterfall, 4.4 m (screen plane) below its top. At the default view height of
44 m (§3.4.8) the top of the fall sits 60 % up the screen, the plunge pool about a fifth of the way up, the basin
stream below it, and about 29 m of mid-tier meadow above the fall.

**Relief shade.** Painted ground tiles cannot know which way a generated slope faces, so one baked shade factor per
terrain vertex stands in for the upper-left sun (F-03). It is a pure function, evaluated once per vertex when the
terrain mesh is built (§3.3.2), with `gx`, `gz` as defined in §3.1.6:

```text
Projection.ReliefQ(gx, gz) = 1024 + clamp(3 * gx - 2 * gz, -180, 180)        // Q10 brightness multiplier, 0.824–1.176
```

Slopes that rise toward the east face west, into the light, and brighten; slopes that rise toward the north face the
viewer and darken slightly. The factor saturates at a gradient of 0.30 east-west, so ridge flanks and side embankments read as
lit or shaded, gentle ramps (gradient 0.20–0.30 northward) darken by 8–12 %, and flat meadows vary by only a few
percent. Nothing about it changes at run time: there is no light source in the scene.

#### 3.2.5 Back-to-front order (F-03, EC-5)

`Murim.Core.World.PropOrder.BackToFront(PropInstance[] props)` returns the prop indices sorted by `ZCm` descending,
then `XCm` ascending, then index ascending: a total, deterministic order with the northernmost prop first. View walks
this list once and numbers `bank_lip` instances `lipRank = 0, 1, 2 …` and all other instances `propRank = 0, 1, 2 …`
in list order (§2.4).

Why ground depth alone is the right key: every sprite is an upright picture standing on its ground point, and the
viewer looks north and down. Of two upright sprites, the one whose ground point is farther south is always the nearer
one, whatever tier either stands on. A prop's tier and height decide **where** it is drawn (`v` includes `0.8 × YCm`),
never **when**: a mid-tier pine near the embankment top draws before a basin boulder standing farther south, and the
boulder correctly overlaps the foot of the bank in front of it.

#### 3.3.1 Rendering setup and the strictly-2D rule

| Setting | Value |
|---|---|
| Pipeline | URP with the **2D Renderer** (`Renderer2DData`) as the only renderer; HDR off, MSAA off, no post-processing Volume; assets in `Assets/Settings/` |

The haze makes the far ridge and its trees melt into the backdrop (ART-008, ART-010); the lower two tiers stay
clear.

**Strictly-2D rule (F-03, RC-2, RC-5).** These hold for the whole project and are asserted by T-ENG-07 and T-ENG-11:

- Exactly one camera; it is orthographic and its rotation is never written after scene load.
- Every world renderer is a `SpriteRenderer`, or a `MeshRenderer` whose mesh is built at launch by a View builder
  (terrain, water, backdrop) with every vertex at `z = 0`. No mesh comes from an asset.
- No model asset exists anywhere under `Assets/`: nothing imported by `ModelImporter` (`.fbx`, `.obj`, `.blend`,
  `.dae`, `.gltf`, `.glb`, `.3ds`).
- No `Light`, `Light2D`, reflection probe, shadow caster, normal map, or lit shader. World materials use only the
  Shader Graphs named in §3.3.2–§3.3.5, all with the Universal target and the *Sprite Unlit* material type
  (alpha blend, no depth write, no depth test).
- No world sprite is rotated or mirrored (`flipX`/`flipY` off, rotation identity, uniform positive scale): the light
  is painted from the upper left and must stay there.
- Nothing in the scene animates: no Animator, particle system, wind, UV scrolling, audio source, or audio listener.

#### 3.3.2 Terrain layer

`Murim.View.TerrainMeshBuilder` builds 64 flat chunk meshes (8 × 8 chunks of 64 × 64 cells, 4,225 vertices and 8,192
triangles each, 16-bit indices), once at launch. The terrain is one continuous painted layer: the heightfield only
decides where each ground point lands on the screen plane and which paintings blend there.

| Channel | Content |
|---|---|
| Position | `(x, PlaneVCm(z * 100, HeightCm) / 100f, 0)` |
| UV0 (`Vector4`) | surface weights of layers 0–3 divided by 255 |
| UV1 (`Vector4`) | surface weights of layers 4–7 divided by 255 |
| UV2 (`Vector2`) | `(ReliefQ(gx, gz) / 1024f, 0)` (§3.1.7) |
| Color32 | white (the *Sprite Unlit* target multiplies by vertex colour) |

Triangle order is part of the contract: within a chunk, cells are emitted row by row from the chunk's **northern**
row to its southern row (west to east inside a row; each cell split along the diagonal from `(x, z)` to
`(x + 1, z + 1)`), and chunk renderers are ordered north row first (§2.4). Nearer ground is therefore always drawn
over farther ground, which resolves the few places where a bank that drops away northward (the south rim of a pool)
folds over the ground behind it.

Shader Graph `Assets/Shaders/Terrain.shadergraph`: blends the eight layer textures by weight, multiplies by the relief
shade, then applies the atmosphere. **Every layer is sampled by screen-plane position** (`worldXY / 16`, one shared
repeat/trilinear sampler state), so a painted tile always appears exactly as painted, whatever the slope beneath it:
ground tiles as obliquely viewed ground, bank-face tiles (layers 4–5) as a wall seen front-on. To hide tiling at
overview zoom, every layer is also sampled at `worldXY / 73` and the two samples are averaged with weight
`_MurimCoarseBlend = saturate((viewHeight - 30) / 40) * 0.5` on the coarse sample (a global float written by
`CameraRigDriver` when the view height changes). No colliders exist.

#### 3.3.3 Water

`Murim.View.WaterMeshBuilder` builds static flat meshes from §3.1.5 data. Every vertex is a logical point
`(xCm, zCm, LevelCm)` projected with `PlaneVCm`; vertex colour alpha is the opacity, UV0.x is the shore factor.

- **Stream and brook ribbons:** per node five vertices across the path direction at offsets `−(hw + 120)`,
  `−(hw + 50)`, `0`, `+(hw + 50)`, `+(hw + 120)` cm (`hw = HalfWidthCm`), with alpha `0, 1, 1, 1, 0` and shore factor
  `1, 1, 0, 1, 1`. The opaque part ends just inside the waterline and the outer strip fades out across it.
- **Pools:** a fan with the centre (shore `0`), a ring at 60 % of `RadiusCm + 50` (shore `0`), a ring at
  `RadiusCm + 50` (shore `1`), and a ring at `RadiusCm + 120` (shore `1`, alpha `0`), 24 segments.
- **Waterfall:** one quad, `WaterfallWidthCm` wide, centred on the fall column, from the projected first `Waterfall`
  node (top) to the projected last node (bottom). On the screen plane the fall is a vertical strip, about 12.7 m tall at
  defaults; U runs across, V = `1` at the top to `0` at the bottom.
- **Foam collar:** one quad centred on the projected plunge-pool centre, `2.4 × RadiusCm` wide and
  `1.44 × RadiusCm` tall (a ground ring seen obliquely).

Materials: Shader Graph `Assets/Shaders/Water.shadergraph` for ribbons and pools (colour = `water_stream` sampled at
`worldXY / 8`, blended to `water_shore` by shore factor × the shore texture's alpha; then atmosphere); the waterfall
and the collar use `WorldSprite.shadergraph` (§3.3.4) materials with `water_fall` and `water_foam` as their texture.
Sort orders per §2.4. Water is painted and static: no reflection, refraction, or scrolling.

| Sprite | `Resources.Load<SpriteAtlas>("Art/Props/WorldProps").GetSprite(<file name without extension>)`, fetched once per variant at launch (§4) |
| Position | `(XCm / 100f, PlaneVCm(ZCm, YCm) / 100f, 0)`: the sprite pivot is the ground-contact point |
| Scale | uniform `ScalePct / 100f`; rotation identity; no flip |
| Colour | `(t, t, t, 1)` with `t = TonePct / 100f` |
| `sortingOrder` | `DrawOrder.Lips + lipRank` for `bank_lip`, otherwise `DrawOrder.Props + propRank` (§2.4, §3.2.5) |
| Material | `WorldFlora` for the Flora family, `WorldSprite` for everything else |

For every Pine, Bamboo, and Rock instance it also creates one shadow `SpriteRenderer`: sprite `shadow_soft`, same
position, scale `ShadowWidthCm × ScalePct / 40000f` (the sprite is 4 m wide at scale 1), colour white, material
`WorldSprite`, `sortingOrder = DrawOrder.Shadows`. The sprite's pivot sits in its upper-left third, so the shadow
falls to the lower right of the prop, opposite the painted light (ART-008). Shadows draw above terrain, water, and
lips and below every prop.

Both materials use Shader Graph `Assets/Shaders/WorldSprite.shadergraph` (sprite texture × vertex colour, alpha ×
`_Fade`, then atmosphere). `WorldSprite.mat` keeps `_Fade = 1`. Flora instances live under one root object, and
`PropView.ApplyViewHeight(float viewHeight)`, called by `CameraRigDriver` when the view height changes, sets
`_Fade = 1 - saturate((viewHeight - 50) / 14)` on `WorldFlora.mat` and deactivates the flora root while `_Fade` is `0`.
Flora is therefore fully visible up to and beyond the default view, fades between view heights of 50 m and 64 m, and
is absent at overview zoom (ART-007: no high-frequency clutter).

**Budget.** Typical valley: 7,300–8,300 prop renderers plus 1,400–1,950 shadow renderers; at the family caps
14,100 plus 3,600. Because every sprite comes from one atlas page and two materials, Unity batches consecutive
sprites; the frame cost is culling and sorting the visible renderers, with no script work and no allocation. Texture
memory is about 110 MB (one atlas page up to 8192 × 4096, eight terrain tiles, water, and backdrop).

#### 3.3.5 Horizon backdrop

The camera never rotates, so the horizon (`ART-010`) is a screen-anchored layer behind the world: a unit quad
parented to the camera at local `z = 10`, scaled each frame to `(viewWidth, viewHeight, 1)`, Shader Graph
`Assets/Shaders/Backdrop.shadergraph` (no atmosphere), composed in screen UV (`v = 0` bottom, `1` top):

| Element | Placement |
|---|---|
| `backdrop_sky` | stretched over `v ∈ [0.60, 1.00]`; below `0.60` its bottom texel colour (haze `#EFD3A0`) |
| `backdrop_peaks_far` | `v ∈ [0.72, 0.98]`, tiled horizontally at width = 4 × height, `u` offset `Cu / 4800` |
| `backdrop_peaks_near` | `v ∈ [0.66, 0.92]`, tiled likewise, `u` offset `Cu / 2400` |

The backdrop only shows where no terrain or sprite covers the pixel, which by §3.4.5 happens only above the north
ridge crest. With the view at its north limit, at most the top 30 % of the screen lies above the lowest crest point;
ridge-top bamboo and pines stand in the lower part of that band, leaving open sky and the peak summits above them.
At the default view it is hidden. The haze (§3.3.1) brings the crest to the same colour as the bottom of the sky, so
the ridge blends into the horizon with no line and no void.

### 3.4 Camera exploration (F-04)

`Murim.Core.Camera.CameraRig` holds the camera state and advances it with `Tick(in CameraInput input, float dt)`.
`Murim.View.CameraRigDriver` (one `MonoBehaviour`, `LateUpdate`) samples devices, calls `Tick`, writes the camera
position and `orthographicSize`, rescales the backdrop quad, and forwards a changed view height to the terrain blend
global (§3.3.2) and `PropView` (§3.3.4).

#### 3.4.1 View model

The camera is a rectangle sliding over the screen plane; all quantities are plane metres (§2.1).

- State: centre `C = (Cu, Cv)`, view height `H`, target view height `Ht`, velocity `V = (Vu, Vv)`, mode `Free` or
  `Resetting`, plus the drag and zoom-anchor data of §3.4.4. View width `W = H × Aspect`.
- A pointer at normalised device coordinates `(sx, sy) ∈ [-1, 1]²` is over the plane point
  `P(sx, sy) = (Cu + sx·W/2, Cv + sy·H/2)`. There is no ray casting and no terrain query: the view has one fixed
  scale across the whole screen.
- `Murim.Core.Camera.ViewFrame` is the world information the rig needs, built once from §3.1.7 values:
  `BottomV = PlaneBottomCm / 100`, `CrestV = PlaneCrestCm / 100`, `VistaU`, `VistaV`, and the constants
  `WorldWidthM = 512`, `SkyFraction = 0.30`, `MaxPixelsPerMetre = 160`.
- `α(τ) = dt / (τ + dt)` is the smoothing factor used throughout (stable for any `dt`; no overshoot). `dt` is clamped
  to `[0, 0.1]` s.

The projection, rotation, and oblique angle are not part of the state, so no input can change them (EC-4).

#### 3.4.2 `CameraInput`

| Field | Source in `CameraRigDriver` (Input System device polling, no action asset) |
|---|---|
| `PanNorth/South/West/East` (bool) | `W`/`Up`, `S`/`Down`, `A`/`Left`, `D`/`Right` held ("north" = up the screen) |
| `DragHeld` | right mouse button held |
| `ResetPressed` | `Home` or `R` pressed this frame |
| `ScrollNotches` (float) | `Mouse.scroll.y` with the project's Input System setting *Scroll Delta Behavior = Uniform Across All Platforms* (one wheel detent = `1.0`; if the pinned package lacks the setting, `scroll.y / 120`) |
| `PointerNdcX/Y`, `PointerInWindow` | pointer position mapped to `[-1, 1]²`; inside when within the window's pixel rect |
| `Aspect`, `ScreenHeightPx` | `Screen.width / Screen.height`, `Screen.height` |
| `Blocked` | overlay open (§3.5.3) |

Left mouse, middle mouse, and pointer position at the window edges are not read for camera motion (EC-6, EC-13;
CE-2 "middle-mouse drag has no effect").

#### 3.4.3 Suppression and cancel

- `CancelAll()`: velocity `= 0`, drag ends, zoom anchor cleared, `Ht = H`, mode `= Free`, and every pan key and the
  drag button **currently held** become *suppressed*. A suppressed input is ignored until it is seen released.
- `CancelAll()` runs when: `Blocked` turns true; the driver reports focus lost or application paused (covers
  `Alt-Tab` and minimise; EC-7, EC-14); or `PointerInWindow` turns false while a pan key is effectively held or a
  drag is active (EC-7).
- While `Blocked`, all inputs are treated as absent; bounds still run (EC-8, EC-9).
- An input is *new* on the tick it becomes effectively held (held and not suppressed) after not being so on the
  previous tick.

#### 3.4.4 Tick order

1. Clamp `dt`. Compute `hMinEff` and `hMaxEff` (§3.4.5). Update suppression; apply `Blocked` and pointer-exit rules.
2. **Reset request** (`ResetPressed`, not blocked): velocity `= 0`, drag ends, anchor cleared, mode `= Resetting`,
   currently held pan keys and drag become suppressed (EC-11).
3. **Reset cancel:** in `Resetting`, any new pan key, new drag, or non-zero scroll sets mode `= Free` and `Ht = H`;
   that input is then processed normally this tick (EC-12).
4. **Scroll** (`n = clamp(ScrollNotches, -4, 4)`, `n ≠ 0`): `Ht = clamp(Ht × f, hMinEff, hMaxEff)` with
   `f = 1 / (1 + step·n)` for `n > 0` (zoom in) and `f = 1 + step·(−n)` for `n < 0`, `step = zoomStepPct / 100`.
   If the pointer is in the window, the plane point `A = P(sx, sy)` and `(sx, sy)` become the zoom anchor; otherwise
   the anchor is cleared (zoom about the screen centre).
5. **Drag start** (new drag, pointer in window): drag becomes active, velocity `= 0`, anchor cleared; the grab point
   is `G = P(sx, sy)`. **Drag end** (drag active, button no longer effectively held): velocity `=` drag velocity
   limited to `2 × panSpeedPerViewHeight × H`.
6. **Motion.**
   - `Resetting`: `C += (Vista − C)·α(resetSmoothTimeS)`; `Ht = clamp(defaultViewHeightM, hMinEff, hMaxEff)`;
     `H += (Ht − H)·α(resetSmoothTimeS)`. When `|Vista − C| ≤ 0.002·H` and `|Ht − H| ≤ 0.002·H`, snap to the target
     and set mode `= Free`.
   - `Free`: `H += (Ht − H)·α(zoomSmoothTimeS)`, snapping `H = Ht` once `|Ht − H| ≤ 0.001·H`. If no drag is active:
     `axis = (East − West, North − South)` from effectively held keys (opposites cancel, EC-1); a non-zero axis clears
     the zoom anchor; `Vtarget = normalize(axis) × panSpeedPerViewHeight × H`;
     `V += (Vtarget − V)·α(axis ≠ 0 ? panAccelTimeS : panStopTimeS)`; `C += V·dt`; with a zero axis,
     `|V| < 0.001·H` snaps `V` to `0`. While a drag is active, pan keys are ignored (EC-2).
7. **Pointer constraints** (mode `Free`), using the new `H` and `W` so the constrained point is exact this tick:
   - drag active: `shift = G − P(sx, sy)`; `C += shift`; if `dt > 0`, drag velocity
     `+= (shift / dt − dragVelocity)·α(0.06)`.
   - else zoom anchor set: `C = A − (sx·W/2, sy·H/2)`. The anchor is cleared once `H = Ht`.
8. **Bounds** (§3.4.5).
9. Publish `(Cu, Cv, H)`.

Initial state: `C = Vista`, `H = Ht = clamp(defaultViewHeightM, hMinEff, hMaxEff)`, mode `Free`, then bounds.

#### 3.4.5 Bounds and the no-void rule (EC-3, EC-4, EC-8)

```text
hMinEff = max(minViewHeightM, ScreenHeightPx / MaxPixelsPerMetre)
hCap    = min(WorldWidthM / Aspect, (CrestV - BottomV) / (1 - SkyFraction))
hMaxEff = max(hMinEff, min(maxViewHeightM, hCap));      H and Ht are clamped to [hMinEff, hMaxEff]
Cu      = clamp(Cu, W / 2, WorldWidthM - W / 2)
Cv      = clamp(Cv, BottomV + H / 2, CrestV + SkyFraction * H - H / 2)
```

A clamped axis has its velocity component set to `0` (no bounce). Why this is sufficient: the terrain always covers
the plane rectangle `u ∈ [0, 512]`, `v ∈ [BottomV, CrestV]` (§3.1.7), the view rectangle never leaves `u ∈ [0, 512]`
or drops below `BottomV`, and anything it shows above the crest is the backdrop, which always fills the screen
(§3.3.5). `SkyFraction` limits how much of the screen may lie above the lowest crest point, so the sky never takes
over the view. `hCap` keeps the view no wider than the world on very wide windows by limiting zoom-out instead of
exposing the sides (it binds only on windows wider than about 5.8:1 at defaults). Aspect ratios wider than 5.5:1 are
unsupported. Bounds are recomputed every tick from the current aspect and window height, so resizing re-clamps within
one frame.

#### 3.4.6 Crisp sprite layering across zoom (EC-5)

- **Crispness.** World art is authored at 128 px per plane metre. At the closest zoom the screen shows
  `ScreenHeightPx / hMinEff` pixels per metre: 90 on a 1080-pixel-tall window, 120 at 1440, and never more than
  `MaxPixelsPerMetre = 160` (1.25× the art) on any window, because `hMinEff` rises on windows taller than 1,920
  pixels. Art is therefore shown at or below its native resolution on common windows and is never enlarged beyond
  1.25×. Every world texture has mipmaps with trilinear filtering, so zooming out does not shimmer.
- **Stable order.** Draw order is fixed at launch (§2.4): each prop has its own `sortingOrder`, terrain triangles
  have a fixed sequence, and there is no depth buffer. The order does not depend on the camera, so panning and
  zooming cannot make anything flicker, pop, or swap. Props always draw above the terrain layer, and nearer props
  above farther ones (§3.2.5), so a foreground object never draws behind background terrain or props.
- The camera has no height above the world and no terrain following: a 2D view cannot clip into terrain or props.

#### 3.4.7 Feel: values and representative numbers

| Quantity (16:9) | `H = 12` (closest) | `H = 44` (default) | `H = 88` (widest) |
|---|---|---|---|
| View width (`1.7778·H`) | 21.3 m | 78.2 m | 156.4 m |
| Flat ground depth in view (`H / 0.6`) | 20.0 m | 73.3 m | 146.7 m |
| On-screen scale on a 1080-pixel-tall window | 90 px/m | 24.5 px/m | 12.3 px/m |
| Key pan speed (`0.9·H`) | 10.8 m/s | 39.6 m/s | 79.2 m/s |

- **Screen-consistent panning:** crossing one 16:9 screen width takes `1.7778 / 0.9 = 1.98 s` at every zoom (CE-1).
  Pan speed is a screen-plane speed, so diagonals (normalised axis) and cardinals cover the same screen distance per
  second in every direction.
- **Dragging** is exactly 1-to-1 at every zoom: the plane point under the cursor stays under it (CE-2).
- **Damping:** pan reaches 95 % speed in 0.32 s; after release it glides `0.22 × speed` (20 % of `H`, about 11 % of a
  screen width) and is within 5 % of rest in 0.68 s. A zoom step is 95 % complete in 0.38 s. Reset is 95 % complete
  in 1.07 s.
- **Zoom range:** 12 m to 88 m is 7.3×, or 15 wheel detents at 15 % per detent; from the default view, 10 detents in
  and 5 out.
- **Valley scale:** the valley floor between the side ridges is `440 − 72 = 368 m`, i.e. `368 / 156.4 = 2.35` screens
  across at widest zoom (F-01 "roughly 2 to 3 screens"). The valid range of `maxViewHeightM` keeps this between 2.07
  and 2.96.

## 4. Art delivery contracts

The owner obtains and commits all art (see [decisions](../decisions.md)); implementers integrate it and do not create
or substitute art. Every `v0.1.0` art file is a flat 2D painting: **no 3D model file of any kind is delivered or
accepted** (§3.3.1). Files go under `Assets/Resources/Art/` with exactly these names.
`Assets/Editor/ArtImportPostprocessor.cs` applies the import settings; the `art` suite (T-ART-01–T-ART-04) checks
every rule here. Each delivered family is credited in [ART_README](../../Assets/Art/ART_README.md). The images in
`docs/references/` are direction only and are never copied into `Assets/`.

**Common rules for all world art (ART-001–ART-008).**

- **View.** Painted as seen in the game: straight-on from the south, looking down from 36.87° above the horizon, with
  no perspective convergence. Widths are drawn at 100 %, vertical heights at 80 %, and ground depth at 60 % (a 10 m
  circle on the ground is an ellipse 10 m wide and 6 m tall).
- **Scale.** 128 pixels = 1 metre of screen plane, at the image's full size.
- **Light.** Warm late-afternoon sun from the upper left, painted in: lit upper-left surfaces, cooler shaded
  lower-right sides. Objects may darken where they touch the ground, but no cast shadow is painted onto the ground
  around them; the `ART-008` shadow sprite supplies it.
- **Format.** PNG, 8 bits per channel, sRGB, straight alpha where RGBA, exact pixel sizes as listed, no text,
  signatures, or watermarks.

**Seamless tile rules.** RGB, tiles without a visible seam on all four edges, no single feature that would make the
repeat obvious (no lone large stone, flower clump, or stain), no object shadows. Import: texture type Default, sRGB
on, mipmaps on, Trilinear, wrap Repeat, compression High Quality, max size = native.

**Sprite rules.** RGBA with a fully transparent background (alpha 0, no matte or halo); the outer 4 pixels of the
canvas are fully transparent unless stated; the canvas and pivot are exactly as listed, with the pivot given in pixels
from the bottom-left corner. The object's ground-contact centre sits on the pivot: what is painted below the pivot row
is the near side of its base, sunk slightly into the ground so it never appears to float on a slope. "Top" is the
height of the highest opaque pixel above the pivot row; widths are bounded by the canvas. Import: texture type Sprite
(2D and UI), Single, 128 pixels per unit, custom pivot (the listed pixel position divided by the canvas size), mesh
type Tight, mipmaps on, Trilinear, wrap Clamp, alpha is transparency, compression High Quality, max size 4096.

**Sprite atlas (integration asset, ARCH-007).** `Assets/Resources/Art/Props/WorldProps.spriteatlas` packs every
sprite under `Assets/Resources/Art/Props/` into **one** page: max texture size 8192, padding 8, rotation off, tight
packing off, mipmaps on, Trilinear, sRGB, compression High Quality, Include in Build on.

## 9. Risks and technical decisions

| Topic | Decision and reason |
|---|---|
| Logical 3D world, strictly 2D picture | Core keeps real positions and heights (three tiers, slopes, water levels, prop heights) so later versions can build, bridge, and fly in XYZ; View only projects them. Nothing 3D is drawn: no models, lights, or depth buffer (§3.3.1). |
| Fixed 3-4-5 oblique projection | Ground depth at 60 % and height at 80 % are exact fractions, so the projection is integer-exact in Core and identical in tests, Editor, and player. They are constants, not tunables: all art is painted for this view. |
| Terrain as one painted layer | The terrain is flat geometry generated in code whose only job is to place painted tiles on the screen plane; tiles are sampled by screen position, so paintings are never stretched over slopes. It is not a model asset and has no thickness. True overhangs cannot exist in a heightfield, so the `ART-002` overhang lip is a sprite placed along embankment tops. |
| Baked light | The sun is painted into every asset from the upper left. Generated slopes get a fixed relief shade (§3.1.7) and props a separate shadow sprite. Consequence: sprites are never mirrored or rotated, so variety among copies comes from scale and a small tone range only. |
| Depth sorting by ground depth | One rule orders every prop, on any tier: farther north draws first (§3.2.5). It is exact between props and, because every embankment faces the viewer, exact against the terrain almost everywhere. |
| Sorting limit beside side-on banks | Props always draw above the terrain layer. Where an embankment runs north-south, a low-tier prop standing right at its foot is drawn in front of the bank rather than partly behind its near edge. This reads as "standing in front" and never flickers; accepted for `v0.1.0`. |
| Integer-only generation | Guarantees identical valleys across the .NET test host, Editor, and player without relying on floating-point contraction rules; lets one golden hash verify all three. Cost: formulas are written in fixed point. |
| Constructive generator | Invariants (three tiers, one waterfall and stream, one ramp per tier pair, south-facing embankments) hold by construction for every seed, so no retry loop or validation-and-reject step exists. |
| One waterfall drop | The waterfall falls about 11 m from the mid tier to the basin head, fed by a spring-pool brook; the upper tier has no water. This reads unambiguously as "one primary waterfall" and keeps the stream in the basin. |
| Screen-anchored horizon | With a non-rotating camera a screen-space backdrop needs no far scenery and cannot leave a void. It appears only above the north ridge, by the bounds rule, and never fills more than 30 % of the screen above the crest. |
| Bounds by view rectangle | The terrain provably covers a fixed rectangle of the screen plane (§3.1.7), so clamping the view rectangle to it makes "no void at any zoom, edge, or aspect" a simple, testable inequality (T-CORE-29). Very wide windows limit zoom-out instead of exposing the sides. |
| Closest zoom tied to art resolution | The closest zoom is 12 m of view height and never shows art above 1.25× its native 128 px/m, which is what keeps sprites crisp (EC-5). Very tall windows therefore zoom in slightly less. |
| Camera model in Core | The motion model has no engine dependency, so every control and edge case is verified deterministically in the fast `core` suite; engine tests cover only device wiring. |
| Pointer leaving the window | Following EC-7 literally, the pointer leaving the window stops keyboard panning as well as dragging; keys must be pressed again. Keys held across the overlay, a reset, or focus loss behave the same way. |
| Seed override | Command line `-seed <0…4294967295>`; the only external input besides the two JSON files. Invalid values are ignored with a warning and never echoed. |
| Config validation | Whole-file fallback on any error keeps behaviour predictable; size (64 KiB), depth (4), schema, and range checks run before values are used; file names are fixed literals so there is no path traversal. |
| Logs and privacy | Game logs record seeds, hashes, counts, timings, file names, and field names only; no local paths, user, or machine names. Unity's own log preamble is engine output outside this rule. No analytics or crash upload. |
| No dev controls | Playtests need only the seed override and the log; nothing debug-only is built, so there is nothing to gate out of release builds. |
| Art dependency | Implementers may not substitute art, so ARCH-005, ARCH-007, and ARCH-008 each wait on their art gate; ARCH-004 lands first so the owner can validate deliveries early. World art is 8 seamless ground tiles, 7 water and backdrop paintings, and 18 sprites; the atmosphere tint and haze (`ART-008`) and the `Paused` title treatment (`ART-011`) are engine values rather than image files. |
| One sprite per prop | Each prop is an ordinary `SpriteRenderer` with a fixed order, the standard Unity 2D path, so later moving units can sort among the same props. Source sprites live under `Assets/Resources/Art/` beside the atlas, so the build may carry them twice on disk (tens of megabytes at most); accepted to keep one art folder. |
| Engine and SDK pins | Unity 6.3 LTS is the current LTS stream with support through the life of this version; the exact patch and package versions are frozen by ARCH-001. .NET 10 is the current LTS SDK. Mono backend avoids an IL2CPP toolchain requirement for contributors. |
| Company name | No studio name is on record, so the player company name equals the product name; changing it later only moves the log/registry folder. |
| Seeds across versions | A seed reproduces a valley only for the same build and `world.json`; later versions may change generation and will then update the golden hashes through their own technical spec. |
| Performance | The scene is static 2D: cost is sprite culling and fill. Flora (about three quarters of all props) is switched off at overview zoom. If PT-1/PT-2 show frame drops, density (`world.json`) is the first lever. |

### 9.1 Values changed by the 2D amendment

The valley itself (size, tier heights, ramps, water, prop placement and density) is unchanged from the earlier 3D
draft. Camera and presentation values were re-derived for a flat, orthographic picture:

| Value | 3D draft | Now | Reason and effect |
|---|---|---|---|
| Closest zoom (16:9 view width) | 15.5 m | 21.3 m | Painted sprites have a fixed resolution; 21.3 m keeps them at or below native size on common windows. Close-up detail is slightly less magnified |
| Default zoom (view width) | 77.6 m | 78.2 m | Same composition; the vista now centres on the waterfall because an orthographic view shows equal ground above and below the centre |
| Widest zoom (view width) | 155.3 m | 156.4 m | Valley floor stays about 2.4 screens across (F-01) |
| Zoom range | 10× in 17 detents | 7.3× in 15 detents | Follows from the closest zoom |
| Key pan | one screen width in 1.99 s | one screen width in 1.98 s | Same feel, now defined on view height (`0.9 × H`) |
| Camera height following, 3 m clearance | present | removed | `EC-5` no longer asks for it; a 2D camera cannot clip |
| Horizon reveal at the north limit | 16–21 % of the screen | at most 30 % above the lowest crest point, part of it behind ridge-top trees | Similar open sky; now an exact rule instead of a measured outcome |
| Flora at overview | fades 80–100 m from the camera | fades between view heights 50 m and 64 m | Same intent (ART-007), expressed for a camera without distance |
| Prop variety | random rotation | scale range plus 92–100 % tone | Rotating or mirroring a sprite would move its painted light |
| Light and shadow | one directional sun with real-time shadows | painted light, baked relief shade, one shadow sprite | Product amendment (F-03, ART-008) |
