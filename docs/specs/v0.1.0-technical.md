## 1. Overview

The repository holds no Unity project yet, so `v0.1.0` first bootstraps one (Unity 6.3 LTS, URP, Input System,
uGUI/TextMesh Pro) with the standalone .NET Core test project and `tools/verify-all.sh`. On top of that:

- **`Murim.Core`** generates the valley from a 32-bit seed using integer-only arithmetic (512 m × 512 m heightfield at
  1 m resolution, water features, surface weights, prop instances, camera height maps) and owns the camera motion
  model (pan, drag, zoom, reset, bounds, terrain following) as a pure, frame-stepped state machine.
- **`Murim.View`** resolves the seed, loads tunables, builds terrain/water meshes, draws props with GPU instancing,
  sets up lighting and the horizon backdrop, feeds input into the Core camera rig, and shows the `Esc` overlay.

**Compatibility.** First version: there are no earlier saves, configs, or dev commands to preserve. Seeds are only
guaranteed to reproduce a valley within the same build and the same `world.json`.

**External surfaces (untrusted input).** Two JSON files under `Assets/StreamingAssets/Data/` and the `-seed`
command-line argument (§2.5, §3.1.1). No networking, saves, telemetry, crash upload, or mod surface.

**Logs and privacy.** Game log lines carry seeds, hashes, counts, timings, config file names, and field names only;
never local paths, user names, or machine names (§2.6).

**Developer controls.** None. `v0.1.0` ships no dev console, debug command, cheat, or debug overlay, so nothing needs
gating; release builds are additionally built without `Development`, `AllowDebugging`, or Profiler options (§3.6.4).
The seed override is a product feature (F-01) and stays available in release builds.

## 2. Conventions and shared contracts

### 2.1 Units and coordinates

- World space is Unity's left-handed, Y-up space. **+X = east (screen right), +Z = north (screen up/far), +Y = up.**
  1 unit = 1 metre.
- The generated terrain rectangle `T` spans `x, z ∈ [0, 512]` m. Core stores positions and heights as **integer
  centimetres** (`…Cm`) and grid data per vertex on a 513 × 513 grid indexed `z * 513 + x` (x, z in metres).
- Angles are degrees. Yaw `0` faces +Z, yaw `90` faces +X (Unity Y rotation).
- Fixed point "Q10" means an integer where `1024` = 1.0.

### 2.2 Determinism rules

- `ValleyGenerator.Generate(seed, config)` uses **only** 32/64-bit integer arithmetic (`unchecked`), `Isqrt`, and the
  primitives in §3.1.2. No `float`/`double`, no `System.Random`, no clocks, no threads, no `GetHashCode()`, no
  dictionary/hash-set iteration order.
- In §3.1–§3.2 every `/` is **floor division** (`FloorDiv`, rounding toward −∞) and every `>>` is an arithmetic shift.
  Loops over the grid run `z` outer, `x` inner, ascending.
- The Core camera model (§3.4) is not part of seeded generation and uses `float`. It must not call
  `Math`/`MathF` transcendental functions (project invariant for all of `Murim.Core`); the trigonometric values it
  needs are the literal constants in §3.4.1.
- The same seed and `world.json` produce the same `ValleyWorld.Hash` in the standalone .NET test host, the Unity
  Editor, and the built player (T-CORE-05, T-ENG-03, T-BLD-02).

### 2.5 Configuration loading

Two files, both optional at runtime, both shipped with their defaults:

| File | Owner section | Consumed by |
|---|---|---|
| `Assets/StreamingAssets/Data/world.json` | §3.1.9 | `ValleyGenerator` |
| `Assets/StreamingAssets/Data/camera.json` | §3.4.9 | `CameraRig` |

`Murim.View.JsonConfigLoader.TryLoad<TDto>(string fileName, out TDto dto)` applies these rules in order; any failure
logs **one** warning naming the file name and the reason code, and the caller uses the built-in defaults for the
**whole file** (no partial application):

1. `fileName` must be one of the two literal names above. The path is always
   `Application.streamingAssetsPath + "/Data/" + fileName`; no caller-supplied directories, no `..`.
2. Missing file → reason `missing`.
3. File length above `65536` bytes (64 KiB) → reason `oversized`; the file is not read.
4. Bytes decode as UTF-8 (a leading BOM is skipped). `JsonGuard.MaxDepth(text)` (counts `{`/`[` nesting outside
   string literals) above `4`, or unbalanced nesting → reason `malformed`.
5. `JsonUtility.FromJson<TDto>` throws → reason `malformed`. DTOs are flat `[Serializable]` classes of `int`/`float`
   fields; unknown JSON fields are ignored.
6. `schemaVersion != 1` → reason `schema`.
7. Core validation (`WorldConfig.TryCreate` / `CameraConfig.TryCreate`) rejects any field outside its range (§3.1.9,
   §3.4.9), any non-finite float, or any violated cross-field rule → reason `range:<fieldName>`. Because every valid
   range excludes `0`, a missing field (deserialised as `0`) is rejected by this step.

`float` fields are parsed by `JsonUtility` (culture-independent). Any other numeric parsing in the project uses
`CultureInfo.InvariantCulture`. The loader reads through one internal file-access delegate (file name → length and
bytes) so engine tests can supply file contents without touching the shipped files.

### 2.6 Logging

All game logging goes through `Murim.View.GameLog.Info/Warn(string)`, which prefixes `[Murim] `. Messages are built
only from: literal text, seeds, hashes, counts, millisecond timings, the two config file names, field names, and
exception **type names** (never `Exception.Message` or stack traces, which can contain absolute paths). Required lines:

| When | Line |
|---|---|
| World built | `[Murim] World ready seed=<uint> source=<cli or random> hash=<16 hex digits> props=<int> ms=<int>` |
| Config fallback | `[Murim] Config <fileName> ignored (<reason>); using defaults.` |
| Bad seed argument | `[Murim] Ignoring invalid -seed value; using a random seed.` (the raw value is not echoed) |

### 2.7 Developer controls

None exist in `v0.1.0`. If a later version adds any, they must be compiled out of release builds with
`#if UNITY_EDITOR || DEVELOPMENT_BUILD`.

## 3. Feature design

### 3.1 Valley generation (F-01)

`Murim.Core.World.ValleyGenerator.Generate(uint seed, WorldConfig config)` returns an immutable `ValleyWorld`. It is a
constructive pipeline (no rejection sampling): every seed yields a valid valley. Stages run in the order below.

**Shape in one paragraph.** The valley is an amphitheatre opening south toward the camera. A parabolic basin tongue
runs north from the south edge to its head near the centre; the mid tier wraps around it; the upper tier wraps around
that; ridges rise along the west, east, and north edges. Because tier level never decreases northward (§3.1.3), every
embankment faces the camera. A spring-fed brook crosses the mid tier and drops as the single waterfall into a plunge
pool at the basin head; the main stream meanders south and leaves at the south edge. One gentle ramp connects basin to
mid tier and one connects mid to upper tier, on opposite sides of the valley axis.

#### 3.1.1 Seed (EC-10)

- `Murim.Core.Common.SeedArgument.TryParse(IReadOnlyList<string> args, out uint seed)` returns `Absent`, `Valid`, or
  `Invalid`. It uses the first argument equal to `-seed` (ordinal, case-sensitive) and the argument after it. Valid
  values are 1–10 ASCII digits parsing (`NumberStyles.None`, invariant culture) to `0 … 4294967295`. A missing value,
  any other character, more than 10 characters, or overflow is `Invalid`.
- `Murim.View.SeedSource.Resolve()` passes `Environment.GetCommandLineArgs()` (through an internal delegate that
  engine tests replace): `Valid` → that seed (`source=cli`); `Absent` → 4 bytes from
  `System.Security.Cryptography.RandomNumberGenerator` as a little-endian `uint` (`source=random`); `Invalid` → the
  warning in §2.6, then a random seed.
- Example: `MurimLifeGame.exe -seed 20261127`. The seed and world hash of every launch appear in the log (§2.6), so a
  normal launch can be reproduced later.

#### 3.1.2 Primitives

```text
Pcg32(seed, stream)        PCG-XSH-RR 64/32. inc = (stream << 1) | 1; state = 0; Next(); state += seed; Next().
  Next():                  old = state; state = old * 6364136223846793005 + inc;
                           xs = (uint)(((old >> 18) ^ old) >> 27); rot = (int)(old >> 59);
                           return (xs >> rot) | (xs << ((-rot) & 31));
  Bounded(n):              thr = (uint)(-n) % n; loop { r = Next(); if (r >= thr) return r % n; }
  R(lo, hi):               lo + Bounded(hi - lo + 1)                      // inclusive

Hash32(int x, int z, uint salt):
  h = (uint)x * 0x9E3779B1 ^ (uint)z * 0x85EBCA77 ^ salt * 0xC2B2AE3D;
  h ^= h >> 16; h *= 0x7FEB352D; h ^= h >> 15; h *= 0x846CA68B; h ^= h >> 16; return h;

Salt(k)   = Hash32(k, 0x51ED, seed)
S(t)      = (t * t * (3072 - 2 * t)) >> 20            // Q10 smoothstep, t in [0, 1024], 64-bit intermediate
Clamp01(t)= clamp(t, 0, 1024)
Isqrt(a)  = floor(sqrt(a)) for 64-bit a >= 0, computed with integers only

Noise(x, z, cell, salt):                               // x, z >= 0 in metres; result in [-1024, 1023]
  ix = x / cell; iz = z / cell; fx = (x % cell) * 1024 / cell; fz = (z % cell) * 1024 / cell;
  c(i, j) = (int)(Hash32(i, j, salt) & 2047) - 1024;
  n0 = c(ix, iz)     + (((c(ix + 1, iz)     - c(ix, iz))     * S(fx)) >> 10);
  n1 = c(ix, iz + 1) + (((c(ix + 1, iz + 1) - c(ix, iz + 1)) * S(fx)) >> 10);
  return n0 + (((n1 - n0) * S(fz)) >> 10);

Bump(d, inner, outer):                                 // Q10; d = |distance| in metres
  d <= inner ? 1024 : d >= outer ? 0 : S((outer - d) * 1024 / (outer - inner))

AtanDeg(dx, dz):                                       // 0..359, clockwise from +Z toward +X; max error 6 degrees
  ax = |dx|; az = |dz|; if (ax == 0 && az == 0) return 0;
  a = ax <= az ? ax * 45 / az : 90 - az * 45 / ax;
  dx >= 0 && dz >= 0 ? a : dx >= 0 ? 180 - a : dz < 0 ? 180 + a : (360 - a) % 360
```

Noise salts: `Salt(1)` contour wobble 64 m, `Salt(2)` wobble 24 m, `Salt(3)` basin 48 m, `Salt(4)` basin 16 m,
`Salt(5)` plateau 40 m, `Salt(6)` detail 8 m, `Salt(7)` ridge 32 m, `Salt(8)` ridge 12 m, `Salt(9)` bank type 56 m,
`Salt(10)` stone 36 m, `Salt(11)` soil 44 m, `Salt(12)` grove 56 m, `Salt(13)` flower 28 m. Prop rule `r` (§3.2.3)
uses `Salt(100 + r)` and `Salt(200 + r)`.

#### 3.1.3 Layout and tier field

Layout values are drawn from `Pcg32(seed, 1)` **in exactly this order** (metres):

| # | Draw | Result |
|---|---|---|
| 1 | `R(-40, 40)` | `axisX = 256 + draw` (valley axis) |
| 2 | `R(196, 228)` | `headZ` (basin head on the axis) |
| 3 | `R(96, 116)` | `midDepth` (mid tier depth on the axis) |
| 4 | `R(150, 190)` | `bowK` (contour bow at 176 m from the axis) |
| 5 | `R(-12, 12)` | `wfX = axisX + draw` (waterfall column) |
| 6 | `R(0, 1)` | `side = draw * 2 - 1` |
| 7 | `R(72, 124)` | `slope1X = clamp(axisX + side * draw, 112, 400)` (basin→mid ramp) |
| 8 | `R(72, 132)` | `slope2X = clamp(axisX - side * draw, 112, 400)` (mid→upper ramp, opposite side) |
| 9 | `R(-60, 60)` | `exitX = axisX + draw` (stream exit at the south edge) |
| 10–14 | `R(-22, 22)` × 5 | `off[1..5]` (stream meander offsets) |
| 15 | `R(-8, 8)` | `springX = wfX + draw` |

With `mid = config.midTierHeightM * 100` and `upper = config.upperTierHeightM * 100` (cm), per vertex `(x, z)`:

```text
dx     = x - axisX
P      = bowK * 100 * dx * dx / 30976                          // contour bow, cm
slopeQ = 2 * bowK * |dx| * 1024 / 30976;  g = Isqrt(1048576 + slopeQ * slopeQ)   // Q10 gradient length of v
wob    = ((Noise(x, z, 64, Salt(1)) * 1200) >> 10) + ((Noise(x, z, 24, Salt(2)) * 250) >> 10)
v      = 100 * z + P + wob                                      // "northness" field, cm
V1 = headZ * 100;  V2 = (headZ + midDepth) * 100
B1 = Bump(|x - slope1X|, 22, 48);  B2 = Bump(|x - slope2X|, 22, 48);  Wf = Bump(|x - wfX|, 4, 12)
hw1 = 450 + (((mid * 5 / 2 - 450) * B1) >> 10);  hw1 = hw1 + (((250 - hw1) * Wf) >> 10)
hw2 = 500 + ((((upper - mid) * 5 / 2 - 500) * B2) >> 10)       // embankment half-widths, cm
hwv1 = (hw1 * g) >> 10;  hwv2 = (hw2 * g) >> 10
s1 = S(Clamp01((v - V1 + hwv1) * 1024 / (2 * hwv1)));  s2 = S(Clamp01((v - V2 + hwv2) * 1024 / (2 * hwv2)))
e1 = (v - V1) * 1024 / g;  e2 = (v - V2) * 1024 / g             // signed distance to each boundary, cm
L  = s1 + s2                                                    // tier level, Q10: 0 basin, 1024 mid, 2048 upper
Ht = ((s1 * mid) >> 10) + ((s2 * (upper - mid)) >> 10)
```

Consequences the tests rely on:

- **Embankments** are smoothstep (rounded) drops: 9 m wide for the basin→mid step and 10 m wide for the mid→upper step
  (5 m wide at the waterfall, forming a cliff).
- **Gentle ramps** widen the same profile to `5 × step height` (60 m and 70 m at defaults) within 22 m of
  `slope1X`/`slope2X`, feathering out by 48 m: average gradient 0.20, smoothstep peak 0.30 before terrain noise.
- The wobble's north-south gradient is below 1 (0.56 + 0.31), so `v`, and therefore `L`, never decreases northward.

`ValleyWorld.TierLevelPct[i] = L * 100 / 1024` (`0`–`200`). `ValleyWorld.Slopes[0]` is measured on column
`x = slope1X` with `s1`, and `Slopes[1]` on column `x = slope2X` with `s2`: `Bottom` = the smallest `z` with `s ≥ 16`,
`Top` = the smallest `z` with `s ≥ 1008`, both stored in centimetres with `X = slopeX * 100`.

#### 3.1.4 Height composition

```text
fS    = S(Clamp01((z - 8) * 1024 / 48))                         // south mouth fade: 0 at z <= 8, 1 at z >= 56
tilt  = 200 + 150 * min(z, headZ) / headZ                       // basin tilts 1.5 m down toward the south
basin = tilt + ((Noise(x, z, 48, Salt(3)) * 60) >> 10) + ((Noise(x, z, 16, Salt(4)) * 25) >> 10)
und   = ((Noise(x, z, 40, Salt(5)) * 70) >> 10) + ((Noise(x, z, 8, Salt(6)) * 15) >> 10)
tW = Clamp01((72 - x) * 1024 / 72);  tE = Clamp01((x - 440) * 1024 / 72);  tN = Clamp01((z - 432) * 1024 / 80)
p(t)  = t * (t + 1024) / 2048;  rt = max(tW, tE, tN)
rough = ((Noise(x, z, 32, Salt(7)) * 250) >> 10) + ((Noise(x, z, 12, Salt(8)) * 60) >> 10)
ridge = max(side * p(tW), side * p(tE), north * p(tN)) / 1024 + ((rough * p(rt)) >> 10)
        // side = config.sideRidgeHeightM * 100, north = config.northRidgeHeightM * 100
H     = basin + ((fS * (Ht + ridge + ((und * min(L, 1024)) >> 10))) >> 10)
```

`ValleyWorld.RidgePct[i] = rt * 100 / 1024`. The ridges rise to their maximum at the terrain edge (30 m above the
local tier on the west/east edges, 26 m on the north edge at defaults). The south fade brings every tier and ridge
down to basin level at the south edge, so the row `z = 0` never exceeds 4 m (measured ≤ 2.8 m; needed by §3.4.7).

#### 3.1.5 Water

```text
fallZ       = smallest z with s1(wfX, z) >= 512                  // cliff line on the waterfall column
zPool       = fallZ - 11
tiltAt(zm)  = 200 + 150 * min(zm, headZ) / headZ
plungeLevel = tiltAt(zPool) - 100;  brookLevel = mid + 180       // cm; waterfall drop = brookLevel - plungeLevel
```

| Feature | Definition (cm unless noted) |
|---|---|
| `PlungePool` | centre `(wfX, zPool)` m, radius `800`, level `plungeLevel` |
| `SpringPool` | centre `(springX, fallZ + 36)` m, radius `450`, level `brookLevel` |
| `Brook` | 16 nodes `i = 0..15`: `x = springX*100 + (wfX - springX)*100*i/15`, `z = (fallZ + 32)*100 - 2900*i/15`, half-width `150`, level `brookLevel` |
| `Stream` | Control points `C0..C6`: `z_k = z0 + (-800 - z0) * k / 6` with `z0 = (zPool - 8) * 100`; `x_0 = wfX*100`, `x_6 = exitX*100`, and for `k = 1..5` `x_k = clamp(wfX*100 + (exitX - wfX)*100*k/6 + off[k]*100, (axisX - lim_k)*100, (axisX + lim_k)*100)` with `lim_k = max(0, Isqrt(max(0, headZ - z_k/100) * 30976 / bowK) - 30)`. Phantom end points `2*C0 - C1` and `2*C6 - C5`. Each of the 6 segments is sampled at `j = 0..15` with the uniform Catmull-Rom below, plus the final point `C6`; nodes with `z < -400` are dropped. Node `i` of `n`: half-width `250 + 150*i/(n - 1)`, level `tiltAt(max(0, z/100)) - 100` |
| `Waterfall` | Width `300`. Nodes on column `x = wfX` every 50 cm from `z = (fallZ + 3)*100` down to `z = (fallZ - 3)*100`: `y = max(height(wfX, z) + 20, plungeLevel)`, with the first node's `y = brookLevel`. `height` is the final carved height, linearly interpolated between the two neighbouring vertices in `z` |

```text
CatmullRom(P0, P1, P2, P3, j) per coordinate, j in 0..15:
  (8192 * P1 + (P2 - P0) * j * 256 + (2*P0 - 5*P1 + 4*P2 - P3) * j * j * 16 + (3*P1 - P0 - 3*P2 + P3) * j * j * j) / 8192
```

**Carving.** Two passes change `H`: first `Brook` + `SpringPool`, then `Stream` + `PlungePool`. For each vertex
(position in cm), over the pass's path segments in node order and then its pool:

```text
segment a→b:  den = (b - a)·(b - a);  t = Clamp01(((p - a)·(b - a)) * 1024 / den)          // Q10, skip if den == 0
              q = a + (((b - a) * t) >> 10);  delta = Isqrt(|p - q|^2)
              hw = a.hw + (((b.hw - a.hw) * t) >> 10);  level likewise;  e = delta - hw
pool:         e = Isqrt(|p - centre|^2) - radius;  level = pool level
keep the candidate with the smallest e (first wins ties)
a = S(Clamp01((600 - e) * 1024 / 400));  c = S(Clamp01((200 - e) * 1024 / 250))
H = H + (((level + 50 - H) * a) >> 10)          // shape banks to 0.5 m above water within 2–6 m of the edge
H = H + (((level - 70 - H) * c) >> 10)          // carve the bed to 0.7 m below water
```

After both passes `H = clamp(H, 0, 12000)` and `wd` (per vertex, cm) = the minimum over both passes of `max(e, 0)`.
Both water levels sit at or below the lowest undisturbed ground of their tier (basin floor nominal ± 0.85 m, mid
plateau nominal ± 1.7 m), so no dry ground lies below adjacent water.
The waterline falls about 0.9 m outside the nominal half-width where the bank meets the water at roughly 36°, so the
water mesh (§3.3.3) and terrain never lie coplanar (no flicker, ART-003).

`ValleyWorld.Vista = (wfX * 100, (zPool - 18) * 100)`: the default view centre, in the basin just south of the plunge
pool with the waterfall and the mid-tier meadow above it in frame (CE-4).

#### 3.1.6 Surface weights

Eight terrain layers per vertex, bytes summing to `255`, in `ValleyWorld.SurfaceWeights[i * 8 + layer]`:

| Layer | Surface | Art |
|---|---|---|
| 0 | moss meadow turf | ART-001 |
| 1 | damp dark-slate soil | ART-001 |
| 2 | mossy stone floor | ART-001 |
| 3 | streamside pebble bank | ART-001 |
| 4 | grassy embankment face | ART-002 |
| 5 | earth-and-boulder bank face | ART-002 |
| 6 | hillside slope | ART-002 |
| 7 | ridge forest floor | ART-008 |

```text
gx = H(x+1, z) - H(x-1, z);  gz = H(x, z+1) - H(x, z-1)   (indices clamped to the grid);  G = Isqrt(gx*gx + gz*gz) / 2   // grade, %
b   = S(Clamp01((G - 45) * 1024 / 45))                           // bank face
eb  = S(Clamp01((Noise(x, z, 56, Salt(9)) + 256) * 1024 / 512))  // 0 grassy bank, 1024 earth-and-boulder bank
so  = S(Clamp01((Noise(x, z, 44, Salt(11)) - 200) * 1024 / 360))
st  = S(Clamp01((Noise(x, z, 36, Salt(10)) - 380) * 1024 / 260))
m   = S(Clamp01((G - 15) * 1024 / 30))
site_k = (B_k * ((4 * s_k * (1024 - s_k)) >> 10)) >> 10          // k = 1, 2
hl  = max(site_1, site_2, (m * 614) >> 10)
r   = S(Clamp01((rt - 150) * 1024 / 350))
w   = S(Clamp01((350 - wd) * 1024 / 300))
```

Start with `weight[0] = 1024` and all others `0`. Apply these overlays in order — `(1, so)`, `(2, st)`, `(6, hl)`,
`(7, r)`, `(4, (b * (1024 - eb)) >> 10)`, `(5, (b * eb) >> 10)`, `(3, w)` — where applying `(layer, a)` means: every
weight becomes `(weight * (1024 - a)) >> 10`, then `weight[layer] += a`. Finally `byte_k = weight_k * 255 / sum`, and
the remainder `255 - Σ byte_k` is added to the layer with the largest `weight_k` (lowest index on ties). No layer
depicts a footpath, road, or paving, and nothing in the generator produces linear worn tracks.

#### 3.1.7 Camera height maps

Two 129 × 129 grids at 4 m spacing (`node * 4` m), `short` centimetres:

- `FocusCm`: the mean of `H` over the vertices within ±8 m of the node in both axes (clipped to the grid).
- `ClearanceCm`: the maximum of `H` over the vertices within ±6 m of the node; then, for every prop instance
  (§3.2), nodes within `CanopyRadiusCm + 483` cm of the prop take `max(current, prop.YCm + HeightCm * ScalePct / 100)`.

`Hash` is FNV-1a 64 (offset `14695981039346656037`, prime `1099511628211`) over little-endian bytes of, in order:
`Seed`; the seven `WorldConfig` ints after `schemaVersion` in §3.1.9 order; `HeightCm`; `TierLevelPct`; `RidgePct`; `SurfaceWeights`;
`Stream` nodes; `Brook` nodes; `PlungePool`; `SpringPool`; `Waterfall` nodes; `Slopes`; each prop (`Variant` byte,

Logged as 16 upper-case hex digits.

**Cost.** One pass of about 263 k vertices with nine noise evaluations each, two localised carve passes, and about
8 k props: estimated below 400 ms single-threaded and about 3.5 MB of Core arrays. Generation runs once at launch.

#### 3.3.2 Terrain

`Murim.View.TerrainMeshBuilder` builds 64 chunk meshes (8 × 8 chunks of 64 × 64 cells, 4,225 vertices and 8,192
triangles each, 16-bit indices), once at launch:

| Channel | Content |
|---|---|
| Position | `(x, HeightCm / 100f, z)`; each cell split along the diagonal from `(x, z)` to `(x + 1, z + 1)` |
| Normal | normalised `(-(H(x+1) - H(x-1)) / 200f, 1, -(H(z+1) - H(z-1)) / 200f)` from the full grid (seams match) |

#### 3.3.3 Water

`Murim.View.WaterMeshBuilder` builds static meshes from §3.1.5 data, Y = `LevelCm / 100f`:

- **Stream and brook ribbons:** per node three vertices (left edge, centre, right edge) at `±(HalfWidthCm + 150)` cm
  perpendicular to the path direction; vertex colour red = shore factor (`1` at edges, `0` at centre); UV0 = world XZ
  / 6.
- **Pools:** a fan with centre, a ring at 60 % of `RadiusCm + 150` (shore `0`), and a ring at `RadiusCm + 150`
  (shore `1`), 24 segments.
- **Waterfall:** a ribbon through the `Waterfall` nodes, `WaterfallWidthCm` wide, offset 0.15 m toward −Z, U across,

- **Foam collar:** a horizontal quad of side `2.4 × RadiusCm` centred on the plunge pool, 3 cm above its level.

Materials: Shader Graph `Assets/Shaders/Water.shadergraph` (Lit, smoothness 0.9; albedo = `water_stream` blended to
`water_shore` by shore factor × the shore texture's alpha) for ribbons and pools; stock `Universal Render
Pipeline/Unlit` (transparent, alpha blend) with `water_fall` for the waterfall and `water_foam` for the collar. Water
does not cast shadows.

#### 3.3.4 Props

`Murim.View.PropRenderer` groups `ValleyWorld.Props` by (variant, 128 m cell of a 4 × 4 grid) into prebuilt
`Matrix4x4[]` batches (split at 1,023) and calls `Graphics.RenderMeshInstanced` for each batch every frame with the
batch's world bounds (Unity culls by bounds). Matrix = translate `(XCm, YCm, ZCm) / 100`, rotate Y `YawDeg`, uniform
scale `ScalePct / 100`. At most 16 × 17 = 272 calls per frame, no allocation.

- Pines, bamboo, rocks, lips: stock `Universal Render Pipeline/Lit` (alpha clip 0.5 and Render Face Both where the
  albedo has alpha; smoothness 0; GPU instancing on); cast and receive shadows.
- Flora: Shader Graph `Assets/Shaders/PropFoliage.shadergraph` (Lit, alpha clip 0.5, two-sided, instanced), scaling
  each instance toward its origin by `1 - saturate((cameraDistance - 80) / 20)`; no shadow casting. Flora therefore
  fades out between 80 m and 100 m from the camera and is absent at overview zoom (ART-007: no high-frequency
  clutter).

One material per variant in `Assets/Resources/Materials/Props/`, each referencing that variant's albedo (§4).

**Budget.** Worst case at the caps: about 3.7 M triangles in the world; a typical overview frame draws about
1.5–2 M plus shadow passes. Texture memory about 130 MB plus a 64 MB shadow map.

### 3.4 Camera exploration (F-04)

`Murim.Core.Camera.CameraRig` holds the camera state and advances it with `Tick(in CameraInput input, float dt)`.
`Murim.View.CameraRigDriver` (one `MonoBehaviour`, `LateUpdate`) samples devices, calls `Tick`, and writes the pose.

#### 3.4.1 Lens and pose

Fixed constants in `CameraLens` (not tunable; art is composed for this angle):

| Constant | Value |
|---|---|
| `SinPitch` (sin 40°) | `0.6427876097` |
| `CosPitch` (cos 40°) | `0.7660444431` |
| `TanHalfVFov` (tan 20°) | `0.3639702343` |
| `KTopY`, `KTopZ` | `0.3639702343`, `1.0` |
| `KBotY`, `KBotZ` | `0.9216049851`, `0.5320888862` |

State: pivot `(Px, Pz)`, distance `D`, target distance `Dt`, rig height `Yr`, velocity `(Vx, Vz)`, mode `Free` or
`Resetting`. Pose: `C = (Px, Yr + D·SinPitch, Pz − D·CosPitch)`; rotation is always `(40, 0, 0)`. For a pointer at
normalised device coordinates `(sx, sy) ∈ [-1, 1]²` and `tanH = TanHalfVFov × aspect`, the view ray direction is
`r = (sx·tanH, −SinPitch + sy·TanHalfVFov·CosPitch, CosPitch + sy·TanHalfVFov·SinPitch)`; `r.y < 0` always, and a
point at parameter `t` along `r` lies at view depth `t`.

`α(τ) = dt / (τ + dt)` is the smoothing factor used throughout (stable for any `dt`; no overshoot). `dt` is clamped
to `[0, 0.1]` s.

#### 3.4.2 `CameraInput`

| Field | Source in `CameraRigDriver` (Input System device polling, no action asset) |
|---|---|
| `PanNorth/South/West/East` (bool) | `W`/`Up`, `S`/`Down`, `A`/`Left`, `D`/`Right` held |
| `DragHeld` | right mouse button held |
| `ResetPressed` | `Home` or `R` pressed this frame |
| `ScrollNotches` (float) | `Mouse.scroll.y` with the project's Input System setting *Scroll Delta Behavior = Uniform Across All Platforms* (one wheel detent = `1.0`; if the pinned package lacks the setting, `scroll.y / 120`) |
| `PointerNdcX/Y`, `PointerInWindow` | pointer position mapped to `[-1, 1]²`; inside when within the window's pixel rect |
| `Aspect` | `Screen.width / Screen.height` |
| `Blocked` | overlay open (§3.5.3) |

Left mouse, middle mouse, and pointer position at the window edges are not read for camera motion (EC-6, EC-13;
CE-2 "middle-mouse drag has no effect").

#### 3.4.3 Suppression and cancel

- `CancelAll()`: velocity `= 0`, drag ends, zoom anchor cleared, `Dt = D`, mode `= Free`, and every pan key and the
  drag button **currently held** become *suppressed*. A suppressed input is ignored until it is seen released.
- `CancelAll()` runs when: `Blocked` turns true; the driver reports focus lost or application paused (covers
  `Alt-Tab` and minimise; EC-7, EC-14); or `PointerInWindow` turns false while a pan key is effectively held or a
  drag is active (EC-7).
- While `Blocked`, all inputs are treated as absent; height following and bounds still run (EC-8, EC-9).
- An input is *new* on the tick it becomes effectively held (held and not suppressed) after not being so on the
  previous tick.

#### 3.4.4 Tick order

1. Clamp `dt`. Compute `dMaxEff` (§3.4.7). Update suppression; apply `Blocked` and pointer-exit rules.
2. **Reset request** (`ResetPressed`, not blocked): velocity `= 0`, drag ends, anchor cleared, mode `= Resetting`,
   currently held pan keys and drag become suppressed (EC-11).
3. **Reset cancel:** in `Resetting`, any new pan key, new drag, or non-zero scroll sets mode `= Free` and `Dt = D`;
   that input is then processed normally this tick (EC-12).
4. **Scroll** (`n = clamp(ScrollNotches, -4, 4)`, `n ≠ 0`): `Dt = clamp(Dt × f, minDistance, dMaxEff)` with
   `f = 1 / (1 + step·n)` for `n > 0` (zoom in) and `f = 1 + step·(−n)` for `n < 0`, `step = zoomStepPct / 100`.
   If the pointer is in the window and `Raycast` (§3.4.5) hits, the hit point and `(sx, sy)` become the zoom anchor;
   otherwise the anchor is cleared (zoom about the screen centre).
5. **Drag start** (new drag, pointer in window): drag becomes active, velocity `= 0`, anchor cleared; the grab point
   `G` is the `Raycast` hit, or, if it misses, the ray's intersection with the plane `y = Yr`. **Drag end** (drag
   active, button no longer effectively held): velocity `=` drag velocity limited to
   `2 × panSpeedPerDistance × D`.
6. **Motion.**
   - `Resetting`: `P += (Vista − P)·α(resetSmoothTimeS)`; `Dt = clamp(defaultDistance, minDistance, dMaxEff)`;
     `D += (Dt − D)·α(resetSmoothTimeS)`. When `|Vista − P| ≤ 0.002·D` and `|Dt − D| ≤ 0.002·D`, snap to the target
     and set mode `= Free`.
   - `Free`: `D += (Dt − D)·α(zoomSmoothTimeS)`, snapping `D = Dt` once `|Dt − D| ≤ 0.001·D`. If no drag is active: `axis = (East − West, North − South)` from
     effectively held keys (opposites cancel, EC-1); a non-zero axis clears the zoom anchor;
     `Vtarget = normalize(axis) × panSpeedPerDistance × D`;
     `V += (Vtarget − V)·α(axis ≠ 0 ? panAccelTimeS : panStopTimeS)`; `P += V·dt`; with a zero axis,
     `|V| < 0.001·D` snaps `V` to `0`. While a drag is active, pan keys are ignored (EC-2).
7. **Height** (§3.4.6), from the pivot and distance of step 6.
8. **Pointer constraints** (mode `Free`), using the new `Yr` and `D` so the constrained point is exact this tick:
   - drag active: intersect the pointer ray from `C` with the plane `y = G.y` at `Q`; `shift = (G − Q).xz`;
     `P += shift`; if `dt > 0`, drag velocity `+= (shift / dt − dragVelocity)·α(0.06)`.
   - else zoom anchor set: solve `P` so the anchor `W` projects to `(sx, sy)`: `t = (C.y − W.y) / (−r.y)`,
     `Px = W.x − t·r.x`, `Pz = W.z − t·r.z + D·CosPitch`. The anchor is cleared once `D = Dt`.
9. **Bounds** (§3.4.7).
10. Publish the pose.

Initial state: `P = Vista`, `D = Dt = defaultDistance`, `Yr` = its target (no easing), mode `Free`.

#### 3.4.5 Terrain queries

`CameraTerrain` wraps `HeightCm`, `FocusCm`, `ClearanceCm` (metres out, bilinear, clamped at the grid edge):
`HeightAt`, `FocusAt`, `ClearanceAt`, and `Raycast(origin, dir, out hit)`: march in 0.5 m steps up to 800 m from where
the ray is over `T`; the first sample at or below `HeightAt` is refined with 8 bisections; leaving `T` or the range is a
miss. `Raycast` runs only on scroll and drag-start ticks (at most 1,600 samples), never per frame.

#### 3.4.6 Terrain following and clearance (EC-5)

```text
camXZ  = (Px, Pz - D * CosPitch)
target = max(FocusAt(Px, Pz), ClearanceAt(camXZ) + clearanceM - D * SinPitch)
Yr    += (target - Yr) * α(heightSmoothTimeS)
Yr     = max(Yr, ClearanceAt(camXZ) + 1.5 - D * SinPitch)       // hard floor, applied instantly
```

The camera therefore rests at least `clearanceM` (3 m) and never less than 1.5 m above the highest terrain or prop top
within about 6 m of it, rising smoothly as it approaches tiers, embankments, the waterfall cliff, and canopies. At
closest zoom over open ground it sits 7.7 m above the pivot; over a mature pine stand it lifts to about 17–20 m.

#### 3.4.7 Bounds and the no-void rule (EC-3, EC-4, EC-8)

With `C.y = Yr + D·SinPitch`, `C.z = Pz − D·CosPitch`:

```text
dCap    = (256 * KTopY / tanH - Yr) / SinPitch
dMaxEff = max(minDistance, min(maxDistance, dCap));   D and Dt are clamped to [minDistance, dMaxEff]
tFar    = min(C.y / KTopY, C.y * SinPitch + max(512 - C.z, 0) * CosPitch)
Xext    = tanH * tFar;                                 Px = clamp(Px, Xext, 512 - Xext)
Zmin    = D * CosPitch - (C.y - 4) * KBotZ / KBotY;    Pz = clamp(Pz, Zmin, 480)
```

A clamped axis has its velocity component set to `0` (no bounce). Why this is sufficient: `tFar` is the view depth of
the farthest ground point (taking the lowest possible ground, `y = 0`) that lies inside the terrain's north edge, and
the frustum's half-width at depth `t` is `tanH·t`, so every view ray stays between `x = 0` and `x = 512` until it
either hits terrain or passes over the north edge onto the backdrop; `Zmin` keeps the bottom rays entering above the
south edge row (≤ 4 m, §3.1.4). `dCap` keeps `Xext ≤ 256` on very wide windows by limiting zoom-out instead of
exposing the sides (it binds only on windows wider than about 21:9; at 16:9 with defaults it stays above 150 m).
Aspect ratios wider than 5.5:1 are unsupported. Bounds are recomputed every tick from the current aspect, so
resizing re-clamps within one frame.

Prototype check: 9 × 9 view rays cast from the clamped pose at 13 extreme pivot requests × 4 zooms × 5 aspect ratios
(4:3 to 32:9) on 12 valleys, including the range corners of `world.json`: 0 of about 250,000 rays left the terrain
anywhere but over the north edge.

## 4. Art delivery contracts

The owner obtains and commits all art (see [decisions](../decisions.md)); implementers integrate it and do not create

sRGB on, mipmaps on, Trilinear, Aniso 8, compression High Quality, max size = native, wrap Repeat for seamless
textures and Clamp otherwise. Terrain and water textures are top-down views with **no baked directional shadows**
(the sun in §3.3.1 lights them).

**Common model rules.** FBX (binary), Y-up, 1 unit = 1 m after import (scale factor 1), +Z forward, origin at the
ground-contact centre, one mesh, one material slot, UV0 inside 0–1 without overlap, vertex normals, triangulated, no
rig, animation, cameras, or lights. Each model has one albedo PNG `<model>_albedo.png` beside it. Import: Read/Write
off, mesh compression off, materials not imported, animation and rig off. Heights are measured from the origin
upward and must be within ±10 % of the stated value; footprint and canopy radii are maxima. No LOD meshes in
`v0.1.0`.

## 9. Risks and technical decisions

| Topic | Decision and reason |
|---|---|
| Integer-only generation | Guarantees identical valleys across the .NET test host, Editor, and player without relying on floating-point contraction rules; lets one golden hash verify all three. Cost: formulas are written in fixed point. |
| Constructive generator | Invariants (three tiers, one waterfall and stream, one ramp per tier pair, south-facing embankments) hold by construction for every seed, so no retry loop or validation-and-reject step exists. |
| Heightfield terrain | Simplest structure that gives real 3D tiers for future building and flight. True overhangs are impossible in a heightfield, so the `ART-002` overhang lip is a small mesh placed along embankment tops. |
| One waterfall drop | The waterfall falls about 11 m from the mid tier to the basin head, fed by a spring-pool brook; the upper tier has no water. This reads unambiguously as "one primary waterfall" and keeps the stream in the basin. |
| Fixed pitch 40°, FOV 40° | Constants, not tunables: the backdrop composition and art are authored for this angle. |
| Screen-anchored horizon | With a non-rotating camera a screen-space backdrop is equivalent to a distant skybox and needs no far geometry. It appears only over the north ridge, by the bounds rule. |
| Bounds by frustum footprint | Clamping the pivot from the frustum's ground footprint (not a fixed rectangle) is what makes "no void at any zoom, edge, or aspect" provable and testable (T-CORE-29). Very wide windows limit zoom-out instead of exposing the sides. |
| Camera model in Core | The motion model has no engine dependency, so every control and edge case is verified deterministically in the fast `core` suite; engine tests cover only device wiring. |
| Pointer leaving the window | Following EC-7 literally, the pointer leaving the window stops keyboard panning as well as dragging; keys must be pressed again. Keys held across the overlay, a reset, or focus loss behave the same way. |
| Seed override | Command line `-seed <0…4294967295>`; the only external input besides the two JSON files. Invalid values are ignored with a warning and never echoed. |
| Config validation | Whole-file fallback on any error keeps behaviour predictable; size (64 KiB), depth (4), schema, and range checks run before values are used; file names are fixed literals so there is no path traversal. |
| Logs and privacy | Game logs record seeds, hashes, counts, timings, file names, and field names only; no local paths, user, or machine names. Unity's own log preamble is engine output outside this rule. No analytics or crash upload. |
| No dev controls | Playtests need only the seed override and the log; nothing debug-only is built, so there is nothing to gate out of release builds. |
| Art dependency | Implementers may not substitute art, so ARCH-005, ARCH-007, and ARCH-008 each wait on their art gate; ARCH-004 lands first so the owner can validate deliveries early. Props are true 3D models (required by F-03); this is the largest sourcing effort (17 models). |
| Engine and SDK pins | Unity 6.3 LTS is the current LTS stream with support through the life of this version; the exact patch and package versions are frozen by ARCH-001. .NET 10 is the current LTS SDK. Mono backend avoids an IL2CPP toolchain requirement for contributors. |
| Company name | No studio name is on record, so the player company name equals the product name; changing it later only moves the log/registry folder. |
| Seeds across versions | A seed reproduces a valley only for the same build and `world.json`; later versions may change generation and will then update the golden hashes through their own technical spec. |
| Performance | No LOD meshes in `v0.1.0`: budgets in §3.3.4 keep worst-case geometry within reach of mid-range desktop GPUs, and flora fades out beyond 100 m. If PT-1/PT-2 show frame drops, density (`world.json`) is the first lever. |
